The AI Risk Manager architecture operates on a strict separation of probabilistic machine 
learning intelligence and deterministic financial execution1. Machine learning decision loops 
must never directly execute ungated monetary actions; rather, probabilistic models evaluate risk 
context while deterministic routers enforce business constraints, rate limits, and financial safety 
boundaries1. 
The physical system topology consists of five decoupled service components designed for 
fault-tolerant operation under high webhook traffic volumes3. Incoming order payload webhooks 
land on an asynchronous FastAPI ingestion gateway running on port 80003. Before reaching 
processing queues, incoming payloads pass through an atomic Redis deduplication store 
operating a 24-hour Time-to-Live (TTL) key check to guarantee absolute idempotency3. 
Once deduplicated, payloads enqueue onto a Celery distributed task queue backed by 
RabbitMQ4. Asynchronous Celery workers pass transaction data to a sub-10ms Feature 
Extraction Engine that merges tabular order data with pre-cached character-level Term 
Frequency-Inverse Document Frequency (TF-IDF) string ambiguity scores3. The extracted 
feature vector is ingested by an XGBoost risk classifier, which outputs a calibrated probability of 
Return-to-Origin (
)3. 
The output probability feeds simultaneously into two downstream modules: a SHAP 
TreeExplainer engine that derives local feature attributions (top-three risk contributors), and a 
PostgreSQL database that records an immutable, append-only audit entry3.

config/thresholds.json3. The router executes one of three deterministic actions: Tier 1 
(ALLOW_COD) dispatches standard Cash-on-Delivery fulfillment; Tier 2 (NUDGE_PREPAY) 
triggers an automated call to the Razorpay Sandbox API to generate an incentivized prepaid 
conversion link; and Tier 3 (SOFT_GATE_COD) applies interactive verification flags prior to 
dispatch1. An asynchronous Large Language Model (LLM) copy generator parses the SHAP 
outputs to produce localized WhatsApp outreach copy and merchant explanations, protected by 
a circuit-breaker fallback to static copy templates to ensure the LLM never sits on the critical 
monetary execution path3.

Sub-10ms TF-IDF Address Ambiguity Engine 
To evaluate address vagueness without inducing API latency penalties, character-level TF-IDF 
vectorization is decoupled from execution time3. Fitting vectorizers dynamically per request 
introduces 150ms–300ms of overhead, violating real-time gateway requirements3. 
The vectorizer is fitted once during application startup against a reference corpus of ambiguous 
and incomplete Indian street address patterns (e.g., "near main road", "behind bus stand", 
"house number zero")3. The resulting sparse feature vocabulary matrix is retained in memory3. 
During live inference, incoming address strings are transformed directly using the cached 
vectorizer, and cosine similarity is computed against the pre-fitted bad address matrix3. This 
pre-allocation strategy guarantees p99 feature extraction execution under 8.5 milliseconds3. 
Synthetic Data Generation and Distributional Realism Protocol 
To prevent target leakage and split contamination, synthetic data generation relies on three 
isolated random seeds3: 
1.​ Training Split: 5,000 samples (seed=101), representing standard baseline distributions3. 
2.​ Validation Split: 750 samples (seed=202), used for joint threshold optimization3. 
3.​ Held-Out Test Split: 1,250 samples (seed=303), containing an injected 10% covariate 
shift via unseen pincodes (is_novel_pincode = 1) and extreme cart values 
(is_flash_sale_cart_value = 1)3. 
Target leakage is prevented by enforcing single-directional statistical lookups6. Pincode 
historical RTO rates and novel pincode designations are computed strictly from the historical 
reference split (train.csv)3. The held-out test dataset is never queried to generate reference 
aggregations3.
