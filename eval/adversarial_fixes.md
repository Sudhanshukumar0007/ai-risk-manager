# Adversarial Review Fixes (Day 11)

An adversarial technical audit identified several gaps between claims made in the documentation/README and the actual implementation. All of these gaps have been systematically addressed:

## 1. Webhook Idempotency (Gap 1)
**Issue**: The README claimed webhook idempotency was handled via a Postgres `UNIQUE` constraint, but the code relied on a flawed Redis `SET NX` followed by a `SELECT` then `UPDATE`. This was prone to race conditions if two webhooks arrived at the exact same millisecond.
**Fix**: Refactored `app/api/webhooks.py` to completely bypass Redis. We now rely exclusively on an atomic Postgres `INSERT ... ON CONFLICT DO NOTHING` against a new `webhook_events` table with a `UNIQUE` constraint on the `razorpay_event_id`. This guarantees true transactional idempotency. A concurrency test (`test_concurrent_webhook_ignored`) was added using `asyncio.gather` to verify this behavior.

## 2. Feature Extraction Latency (Gap 2)
**Issue**: The README claimed a ~2.44ms p99 latency, which was only the local feature extraction time, not the full end-to-end request latency (which benchmarks at ~14.1ms).
**Fix**: Updated the `README.md` to accurately reflect the true end-to-end API latency under load, eliminating the misleading claim.

## 3. Transaction Boundaries (Gap 3)
**Issue**: There was a concern that `_insert_audit_log_sync` in `app/services/scoring.py` might leave hanging database locks if an error occurred before `session.commit()`.
**Fix**: Audited the transaction boundaries and confirmed that the SQLAlchemy `Session` correctly limits the transaction to the `try/except` block, safely rolling back on exceptions (like `UniqueViolation`). No code changes were strictly necessary, but the logic was verified.

## 4. Bootstrap CI Scope (Gap 4)
**Issue**: The CI pipeline doesn't natively check whether changes break the expected RTO mitigation *thresholds*—it exhibits structural optimism by only checking if the code runs, not if the tuning holds.
**Fix**: Added a disclaimer to `docs/day11_bootstrap_ci.md` explicitly acknowledging this limitation so future engineers are aware they must manually validate threshold stability after model updates.

## 5. Drift Attribution Evidence (Gap 5)
**Issue**: Documentation claimed the model had "conceptual understanding" of drift, heavily weighting the synthetic `is_novel_pincode` features during a flash sale injection. However, SHAP analysis showed zero marginal weight for these explicit features.
**Fix**: Updated the README and `docs/day11_drift_attribution.md` to downgrade certainty. Acknowledged that the model identifies drift via *correlated proxy features* (e.g., address patterns or numerical artifacts) rather than the intended explicit drift probes.

## 6. Unauthenticated Dashboard (Gap 6)
**Issue**: The internal dashboard at `dashboard/app.py` was exposed with no authentication.
**Fix**: Implemented a stopgap password gate at the top of the Streamlit application. Users must enter a password (configurable via `DASHBOARD_PASSWORD`, defaulting to `risk_admin`) to access the interface. It's explicitly documented as a basic barrier against trivial access, not a substitute for Enterprise SSO/MFA.

## 7. Missing Rate Limiting (Gap 7)
**Issue**: The `/v1/orders/score` endpoint had no rate limiting, exposing the system to denial of service or quota exhaustion attacks.
**Fix**: Implemented a Redis-based fixed-window rate limit directly in `app/api/routes.py`. It limits incoming requests to 100 per minute per IP using atomic `INCR` and `EXPIRE` commands, returning HTTP 429 when the limit is breached.

## 8. Connection Pool Exhaustion (Gap 8)
**Issue**: The total possible connections generated by Uvicorn workers and Celery concurrency exceeded Postgres's default limit of 100, risking `FATAL: sorry, too many clients already` errors under burst load.
**Fix**: Mathematically bounded the connection pools across the fleet. Reduced `app/db/session.py` API pool to `pool_size=5, max_overflow=5`, and `app/services/scoring.py` Celery pool to `pool_size=2, max_overflow=3`. This caps the theoretical maximum connections well below the 100 threshold, even at maximum horizontal concurrency.
